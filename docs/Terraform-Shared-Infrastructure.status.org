#+TITLE: Shared Terraform Infrastructure

* Overview

  Company-agnostic Terraform/OpenTofu infrastructure that any consumer repo can
  adopt, so each repo does not duplicate CI workflows, policy scripts, dev-shell
  tooling, or bootstrap logic. The reusable pieces live here in nixos-modules;
  a consumer repo supplies only its own data (accounts, owners, zones, reviewed
  inventory) and thin-calls the shared modules and drivers.

  The shared agentic workflow is the same for every consumer: agents develop
  offline against mock providers, CI runs a credentialed plan and posts the
  result as a PR comment, a human approves, and CI applies on merge. Scheduled
  drift detection runs against the same backends.

* What is provided

  - *Reusable CI* — the reusable Terraform workflow
    (=.github/workflows/reusable-terraform-ci.yml=), the metadata-driven root
    discovery matrix (=terraform/ci/terraform-ci-matrix=), and the plan-policy
    scripts.
  - *Layer-0 bootstrap* — the AWS module (=terraform/aws/tf-bootstrap.nix=) and
    driver (=terraform/aws/aws-bootstrap=), and the CI-enabling GitHub module
    (=terraform/github/tf-bootstrap.nix=) and driver
    (=terraform/github/github-bootstrap=). See
    [[file:Terraform-Bootstrap-Runbook.md][the bootstrap runbook]].
  - *GitHub governance* — the governance engine
    (=terraform/github/governance.nix=), branch-protection rulesets
    (=terraform/github/branch-protection.nix=), and the import-phase tooling
    (=terraform/github/github-inventory=, =github-governance-import-blocks=,
    =github-governance-import-ci=).
  - *Cloudflare* — the read-only inventory tool
    (=terraform/cloudflare/cloudflare-inventory=), the import-block generator
    (=terraform/cloudflare/cloudflare-import-blocks=, driven by the per-repo
    =import-ids.json=), and the import-only apply harness
    (=terraform/cloudflare/cloudflare-import-ci=) — symmetric with GitHub
    governance. The reviewed adoption data (=default.nix= + =import-ids.json=)
    stays per-repo; the generator and harness are shared.
  - *Methodology* — [[file:Terraform-Agent-Development-Methodology.md][development methodology]],
    [[file:Terraform-Testing.md][testing]], [[file:Terraform-Root-Layering.md][root layering]],
    [[file:Terraform-Import-Phase.md][the import/adoption phase]], and
    [[file:GitHub-Secret-Rotation.md][secret rotation]].

* Consuming a shared module

  A consumer repo's bootstrap root is a thin caller pinned to a nixos-modules
  revision; its Justfile invokes the shared drivers from that pinned source. See
  each module's README under =terraform/= and the bootstrap runbook for the
  end-to-end procedure. Deployment facts (accounts, owners, zones) live in the
  consumer's tracked Terraform/Nix files, never in this shared repo.

* Immutable reusable-workflow source

  Every Terraform job materializes the repository and commit that contain the
  called reusable workflow into =.mcl/reusable-terraform-ci=. GitHub supplies
  that identity through =job.workflow_repository= and =job.workflow_sha=; the
  workflow does not substitute the caller repository/SHA or accept a duplicate
  caller-provided revision. The caller selects the reusable source with its
  literal =uses: metacraft-labs/devops-modules/...@<ref>= declaration, and
  GitHub resolves that selection to the full =job.workflow_sha= used by every
  Terraform job. This is intentionally distinct from =github.sha=, which can
  name the consumer repository's synthetic pull-request merge. The checkout
  action is commit-pinned and does not persist credentials.

  Before Setup Nix runs, each job fails closed unless the local checkout has a
  full commit SHA matching =job.workflow_sha=, an origin matching the called
  workflow repository on the current GitHub server, and a clean worktree. It
  also hashes every tracked Setup Nix source file directly against the called
  commit, so index flags cannot conceal changed action bytes. Setup Nix is then
  invoked as a local composite action from that checkout.

  The plan job repeats the exact HEAD/origin checks immediately before the
  policy gate. It compares both policy files' worktree bytes with blobs selected
  through =job.workflow_sha=, materializes private policy copies directly from
  those content-addressed Git objects, verifies the copies, and executes only
  the copies. This rejects modifications hidden from =git status= with
  =assume-unchanged= or similar index flags. It does not resolve =@main=, use
  =github.action_ref= fallbacks, or download policy bytes from a mutable URL.

  GitHub documents the =job.workflow_*= identity fields for GitHub.com reusable
  workflows and marks them unavailable on GitHub Enterprise Server. An absent
  identity therefore fails closed here; this checkpoint does not claim GitHub
  Enterprise Server compatibility. The origin check derives its host from
  =github.server_url= rather than hard-coding =github.com=, so supported GitHub
  hosts retain their exact repository identity.

  =scripts/tests/test_reusable_terraform_source_identity.py= is an executable
  contract test for all four jobs. It checks exact cardinality and step order,
  requires source checkout, verification, and Setup Nix to remain adjacent,
  and rejects additive source checkouts or Setup Nix/policy executions that
  could bypass the verified path. It exercises the verification shell against
  a real temporary Git repository, proves that ordinary and index-hidden Setup
  Nix, policy-script, and policy-helper byte drift fails, and carries hostile
  mutations for removed, reordered, substituted, unrelated-immutable,
  fallback, credential-persistence, worktree-materialization, and
  weakened-verification cases. The test is wired into the flake as
  =reusable-terraform-source-identity=.

  Local Linux verification establishes the source and shell contracts only.
  After this change lands, real reusable-workflow calls on the supported CI
  runners—including macOS ARM64—remain required operational evidence; no
  Darwin execution result is claimed by this local checkpoint.

* Opt-in GitHub-hosted Nix disk reclamation

  Setup Nix and the reusable Terraform workflow expose
  =reclaim_hosted_runner_disk= as a disabled-by-default boolean. When enabled,
  it runs before any Nix installation or realization, accepts only GitHub's
  immutable =runner.environment= classification =github-hosted= together with
  Linux, and removes exactly the reviewed Android, .NET, GHC, ghcup, and CodeQL
  image paths. Deletion uses non-interactive sudo, is confined to each named
  filesystem, and cannot ignore errors. The helper then fails unless at least
  20 GiB is available on the root filesystem.

  The reusable workflow forwards the same option to offline, plan, apply, and
  drift jobs; its self-hosted runner default and the Setup Nix default remain
  unchanged. =test_setup_nix_hosted_disk.py= verifies the positive helper path,
  rejects self-hosted, non-Linux, out-of-Actions, failed-cleanup, malformed
  measurement, and insufficient-space executions, and carries hostile source
  mutations for default enablement, broadened deletion, weakened runner checks,
  ignored errors, removed postconditions, and incomplete workflow propagation.
  This source checkpoint claims no hosted-runner execution evidence; consumers
  must observe the opt-in on their actual runner image.

* Terraform provider and backend credential composition

  Terraform-root metadata models provider and backend authentication as
  independent axes. =credential_mode= selects provider credentials;
  =backend_uses_aws_oidc=true= additionally supplies the reviewed AWS OIDC role
  to an AWS-backed state backend. This supports token-authenticated providers
  such as Cloudflare, Stripe, or GitHub while retaining an S3 backend without
  private consumer-side matrix logic. An =agenix-token= root whose encrypted
  plan/apply key files are absent remains offline-only even when its backend
  requires AWS OIDC.

  The direct suite covers combined, provider-only, backend-only, legacy AWS
  provider, credential-free, missing-secret, and malformed-metadata cases. The
  flake check runs that suite in a Nix sandbox on every supported system and
  also proves that mutations weakening backend composition, credential
  readiness, defaulting, validation, or matrix publication are rejected.
